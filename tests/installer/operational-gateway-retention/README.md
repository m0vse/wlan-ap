# Durable operational activation across managed boots

An older managed upgrade can archive a birth-certificate gateway while the certificate store already contains the successfully migrated operational gateway. The saved-identity early-boot shortcut previously restored policy but left that archived gateway untouched; cloud discovery then gave its stale flash selector precedence. The operational certificate itself remained intact.

The shortcut now restores discovery policy first, then replays the existing durable operational activation. It requires the same endpoint and strict TLS settings, the recognized old birth selector or matching operational selector, matching Root-owned runtime/store key, leaf and issuer trust, key/leaf match, current validity and client-chain validation. It restores the approved durable EST settings and both runtime gateway selectors. It preserves custom endpoint/CA/policy/EST conflicts and bypasses fresh FORMAT2 defaults. It does not enroll, renew, regenerate a key, change certificate/trust files, or introduce an issuer-specific rule or activation protocol.

Publication is individually atomic in EST→flash→gateway order and replayable after interruption. A failed validation does not replace a selector or identity. An already-selected expired operational identity retains its selection and existing renewal attempt; an expired TLS client certificate may be rejected by the EST server, in which case native renewal preserves the key and leaf. This is not a claim that expired mTLS certificates can renew successfully.

Run `test-operational-restore.py` as Root with `WLAN_AP_SOURCE_DIR` pointing to the source tree, `NATIVE_TEST_UCODE` to an existing target ucode emulator wrapper, and `OW_TEST_ROOT` to an extracted firmware root containing the actual native init script. It uses target ucode, host OpenSSL and synthetic Root-owned files. It executes the actual boot shortcut, discovery pin selection and native client argument construction, old-selector tar replay, second boot, operator conflicts, invalid dates/identity and interrupted publication. Hardware/mount/installer boundaries are isolated.

The native first-boot regression stages the new helper and policy module and additionally exercises restored operational selection/EST settings followed by actual native EST dispatch and target curl over synthetic localhost HTTPS. It tests successful renewal, failed renewal and expired-client mTLS rejection retaining identity and selection. The existing native EST source is unchanged.

These are source/runtime regressions. New images must verify the exact helper, early-boot hook, package release and actual startup behavior before release. No AP is modified by these tests; hardware upgrade/boot acceptance is separate.

Public CA bundles have a separate 2 MiB limit, consistent with the existing EST server-trust limit; private keys and single leaf certificates retain the 128 KiB limit. The cap provides about 9.4 times the observed 223,727-byte bundle size. Tests cover that exact size, exact 2 MiB acceptance, one byte over rejection, and oversized key/leaf rejection with file/size/limit diagnostics. Comparison uses two temporary bundle strings: approximately 0.43 MiB at the observed size or up to 4 MiB at the cap, plus the separate OpenSSL parser/verification process. These are transient boot-helper allocations, not persistent daemon growth.

For an optional public-data regression set `OW_TEST_PUBLIC_CA_BUNDLE`, `OW_TEST_PUBLIC_CA_SHA256` and `OW_TEST_PUBLIC_CLIENT_LEAF`. The supplied bundle is hashed and parsed unchanged, and the supplied public leaf is checked for validity and client-chain trust against it. To exercise synthetic key/leaf activation, only isolated bundle copies receive the synthetic fixture issuer; the receipt records this distinction and the resulting tested bundle size. No real private key is copied or used.

The observed Sage image shipped `/etc/ucentral` as root:root `0775`: a recursive discovery-package copy preserved the build checkout directory mode. All five shared package providers now normalize that directory after copying with OpenWrt's `INSTALL_DIR` (`0755`). Client source/version pins are unchanged; its package release changes only for staging permissions.

Before installer prepare, early boot runs the bounded `ucentral-secure-runtime` migration: a canonical Root-owned, root-group `0775` directory becomes `0755`; existing `0700`, `0750` and `0755` directories keep their permissions and ownership. It rejects symlinks, non-Root ownership, world-write, other-group `0775`, special bits and failed chmod. It changes no files, keys, certificates or trust. The existing restore helpers keep their strict checks. Boot failures log their stage and exit status without credential contents; helper diagnostics remain on stderr.

The activation runner adds the actual legacy-mode boot, safe private modes, unsafe metadata and chmod failure. It verifies installer prepare sees secure permissions, operational native argv, repeated boot, unchanged identity bytes and unchanged rejected selectors/metadata. Set `OW_TEST_SHELL` to a target BusyBox wrapper plus `ash` to execute the boot helper on the packaged shell as well as target ucode. `test-package-runtime-mode.py`, with `OW_TEST_RULES` pointing to actual OpenWrt `rules.mk`, reproduces the old `cp -fpR` mode preservation, executes each corrected package install tail and checks all 120 provider merge orders. These staging tests do not compile firmware.

Main's separately approved live Sage test reproduced the unchanged `.6` helper's directory refusal, changed only canonical root:root `0775` to `0755`, replayed the existing activation and restarted the management client. It confirmed new operational certificate/CA arguments, reconnect and applied configuration with all key/certificate/trust bytes unchanged. That validates the cause and live recovery; a new Sage image still requires actual upgrade and boot acceptance before other families proceed.
