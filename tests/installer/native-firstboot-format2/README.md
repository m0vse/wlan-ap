# Native first-boot FORMAT2 regressions

These tests create synthetic identities and exercise localhost HTTPS only. Never supply a real enrollment key, AP identity or issuer. No AP, service, firmware build or deployment is used.

Stage the committed runtime files into a fresh temporary directory:

```sh
python3 stage-source.py /path/to/wlan-ap /tmp/native-firstboot-fixture
export NATIVE_FIRSTBOOT_SOURCE_DIR=/tmp/native-firstboot-fixture
python3 test-services.py
python3 test-mount.py
python3 test-worker.py
```

For the actual native EST/first-boot helper test, use an existing ARM target root containing ucode/modules and curl, host OpenSSL and qemu-arm. Set `NATIVE_TEST_ROOT` to that target root and `NATIVE_TEST_UCODE` to its existing executable ucode emulator wrapper. Run `test-native-firstboot.py` as Root with these three environment values preserved. Its private temporary files contain only freshly generated synthetic test identities. It verifies failed enrollment/reboot retries, cached CSR integrity, independent HTTPS trust, leaf persistence, native applied-config confirmation and resumable confirmed cleanup.

For the native status callback test, set `NATIVE_CLIENT_SOURCE_DIR` to an isolated checkout of pinned native client 176cab2f with the committed `001-installer-trial-reapply.patch` applied. Run `test-status-width.py` with a host C compiler.

JSON receipts are written into the staging directory. Mount, hardware, UCI, ENV, native status/process and service boundaries are isolated where needed. The HTTPS test executes the actual packaged mount helper with an isolated active-volume mount table, actual native EST dispatch/curl/OpenSSL and the committed identity helper. These tests establish source behavior; they do not establish hardware power-loss, package closure, production onboarding or release readiness.

To qualify the complete committed native client patch stack from its exact pinned Git source, set `WLAN_AP_SOURCE_DIR` to this repository and `NATIVE_CLIENT_SOURCE_DIR` to a checkout containing pinned commit 176cab2f. Run `test-patch-stack.py`. It applies every packaged patch with zero fuzz, refuses the obsolete activation nonce hook, and tests the actual patched status and boot-report transport callbacks. The transport test verifies full-write success and partial-write, error, disconnected and JSON-allocation failures with isolated websocket boundaries.

Clean migration and legacy upgrades are different paths. A qualified OEM or stock-OpenWrt migration delivers private FORMAT2 `est.json`, `est-bootstrap.conf`, `gateway.json`, binding and checksums. The same first-boot worker stages protected settings, waits for network and verified clock, runs the shipped native EST `enroll`, persists the original key/CSR and validated operational identity, then consumes the bootstrap only after observed applied configuration. A managed upgrade preserves an existing birth/manual identity and does not fabricate those settings. Missing EST settings on such an upgrade do not show a failure of the configured clean migration path. Bare firmware without the private enrollment payload is not zero-touch provisioning.

The released Sage `.7` image (`1ff2d0c3`, image SHA256 `10cfd2c8e8b149e72f234701b32aa32dea5eb224fc5749152fd18ae30a79f82b`) independently passed the full synthetic native first-enrollment protocol test, plus its worker and service tests. The protocol test now also invokes the actual packaged `expiry_handler` and `trigger_reenroll` against the same native client and real localhost HTTPS fixture. Missing clock and birth-certificate selection refuse unattended renewal; a service failure retains key/leaf/selectors and does not restart the client; success renews using mTLS without bootstrap credentials, persists the leaf and reaches the client restart boundary. Hardware, mount/context/UCI and restart boundaries remain isolated; OpenSSL is the host implementation. This proves source/runtime behavior, not a completed production OEM/stock hardware migration. The production OEM qualification remains gated pending its separate real-device test.

For the finite legacy APs, use the existing enrollment path rather than a new portal adapter. Before including any serial, read its actual issuer ledger and active campaign membership. An AP with no issued record and no active batch can use AP Certificates → enrollment type **New OpenWiFi APs** → selected serials → **Create enrollment key**. One shared batch covers the selected APs; the **OEM / OpenWrt migration** type requires separate source qualification and is not the choice for an already-running legacy OpenWiFi AP. A serial with an issued legacy record is not eligible for a fresh batch; review its existing native renewal/import path instead. No batch is created by these tests.

The existing AP-side one-time procedure is an operator action, after approval for the named AP:

1. Mount its active certificate store; verify the serial, current strict controller endpoint, birth/key match, runtime/store key equality and readiness. Refuse conflicting operational identity or existing pending installer transaction. Record the current public key digest. Save a protected, durable backup of identity/trust files and both runtime/durable selectors and EST settings, including which files were absent, original owners and modes. Keep the backup directory Root `0700`, files `0600`.
2. Deliver the shared bootstrap through a Root-only file; never place it in chat, logs, shell arguments, history or a script payload. Stage Root `0600` native `est.json` in runtime and durable storage, with the approved private server and existing HTTPS CA; stage Root `0600` `est-bootstrap.conf` with curl Basic settings for this serial and the shared key. Preserve `key.pem` and `cert.pem`; do not prime an operational filename from a birth leaf for this fresh-enrollment route.
3. Run `est_client enroll` directly while the current management client remains connected. The shipped client generates the serial-bound CSR using the existing key, validates the signed leaf and persists the operational files. Before changing selection, verify expected new issuer/root, validity, client purpose, CN equals serial, unchanged key digest, leaf/key match and byte-matching durable leaf. Preserve the original endpoint and hostname validation. Combine the approved new client issuer trust with the original gateway server trust for `operational.ca`; validate both rather than trusting filenames. Keep Root/network `0440` runtime public files and protected durable copies.
4. Atomically persist the approved operational gateway selection to durable `gateway.json`, runtime `gateway.flash` and runtime `gateway.json`, with the same server/port/TLS policy; persist public EST policy. Restart the management client once. Require observed new-issuer verified connection and received/applied configuration, then remove the bootstrap secret from both runtime and durable storage. Retain public EST policy for unattended mTLS renewal and the protected recovery backup.

On failure before switching, preserve the working identity and selection; do not restart it merely because enrollment failed. If rollback is needed, restore only the backed-up identity/trust/selector/EST files, owners/modes and original absence markers in both runtime and durable store, verify original key/birth digests, sync and restart once; verify the original connection. Retain the issuer ledger/signing history and overlap trust. Rollback does not revoke or erase a certificate already signed. This procedure is not executed or hardware-qualified for each remaining AP by the synthetic tests.
